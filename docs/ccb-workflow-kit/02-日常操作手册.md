# 日常操作手册：怎样让 Agent 协作而不互相踩文件

## 推荐任务生命周期

```text
任务进入 → main 定义边界 → scouts 只读摸底 → developer 实现
       → reviewer fresh review → developer 修复（如有）
       → main 验收/请求人工 Gate → knowledge_keeper 归档
```

主控 agent 是流程所有者，不是第二个开发者。代码修改只由 `developer` 进行；所有 reviewer/scout/utility 都保持只读。

## 派发任务

从 CCB 的 main pane 使用 `ask`。提交一个任务后不要在同一任务上反复 `pend/watch/ping`；等待最终回复。消息需要包含身份、目标、范围、假设、输出和验证要求。

```bash
ask task_scout '你是 task_scout（只读任务/依赖侦察）。目标：梳理 Issue #123 的影响范围。范围：只读 docs/、相关模块和现有测试；禁止写文件。输出：发现、涉及文件、风险、建议验证命令。'

ask developer '你是 developer（唯一代码写者）。目标：按已确认方案实现 Issue #123。范围：仅指定模块和你的 CCB worktree；禁止修改 .env、禁止提交/推送。先报告实施计划，再实施。输出：变更、验证、风险、待人工确认项。'

ask reviewer '你是 reviewer（每轮 fresh 只读审查）。目标：审查当前 exact-HEAD diff。范围：只读，不修改文件。输出按严重度列出可复现 findings（文件:行、影响、建议）；无问题明确写“未发现阻塞项”。'
```

`ask --chain` 只用于“当前任务没有子结果就无法继续”的依赖链；互不依赖的侦察使用普通 `ask`。仅需执行且不需要结果的工作可用 `ask --silence`，但它不能用来更正正在进行的任务。

## 上下文管理

- 一个任务内：developer 在实现与 review 修复之间保留上下文；不要每次调用都 clear。
- 跨任务：已经完成后才对将复用的 developer、knowledge_keeper、scout/explorer/utility clear。
- reviewer：每一轮完整审查前必须 fresh。使用 `ccb clear reviewer`，确认完成后再派发本轮审查。
- 取消：运行时中断是首选手段。已取消任务不要再继续写入或发送外部结果。

## Git 与 worktree

1. main 先确认基线、任务分支和 worktree 策略。
2. developer 是唯一代码写者，且只在其 CCB worktree 修改。
3. reviewer 审查 exact HEAD，而不是过期 diff 或猜测的分支。
4. 提交、推送、创建/合并 PR、发布、数据库迁移和生产操作均需项目规则或负责人明确授权。
5. developer 停止后，knowledge_keeper 才能写同一个 worktree 的文档/记忆。

## 常用控制命令

| 目的 | 命令 | 注意 |
| --- | --- | --- |
| 启动当前项目 | `ccb` | 在项目根目录执行 |
| 安全启动 | `ccb -s` | 禁用 CLI 自动权限覆盖 |
| 配置界面 | `ccb config ui` | 仅 loopback；不要共享 token |
| 配置预演 | `ccb reload --dry-run` | 先做此操作 |
| 应用安全增量 | `ccb reload` | 结构性变更可能被拒绝，按提示重启 |
| 健康检查 | `ccb doctor` | 只读诊断 |
| 诊断单 agent | `ccb ping reviewer` | 仅诊断，不是催办方式 |
| 清 reviewer | `ccb clear reviewer` | 每轮审查前 |
| 重启空闲 agent | `ccb restart reviewer` | 确认无活跃任务 |
| 停止当前项目 | `ccb kill` | 核对当前目录 |

## 人工 Gate

涉及登录扫码、验证码、微信/苹果/Google 控制台、真实支付/退款、生产发布或删除数据时，agent 必须停在可操作入口，向负责人说明：入口、最短步骤、需要回传的结果。不要索要密码、token、密钥或浏览器 Cookie，也不要通过聊天传递它们。
