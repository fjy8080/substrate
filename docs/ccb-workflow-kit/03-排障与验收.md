# 前检、冒烟验收与排障

## 10 分钟最小验收

1. 在目标项目运行 `./scripts/preflight.sh`，确认 CCB、Codex、Claude、git、tmux 和 Node/npm 可执行。
2. 运行 `ccb doctor`，解决 PATH、Node 版本和 provider 可执行文件问题。
3. 在项目根目录运行 `ccb`，检查 `main`、`reviewer`、`developer`、`task_scout`、`explorer`、`utility`、`knowledge_keeper` 的 pane 是否出现。
4. 从 main 发一条只读任务给 `task_scout`：让它只列出仓库顶层目录。收到简洁结果即可。
5. `ccb clear reviewer`，从 main 发给 reviewer：让其只读检查 `git status --short`，不得写文件。
6. 确认 developer 的 pane/worktree 存在，但不派发真实修改。
7. 运行 `ccb kill`，再 `ccb` 重启，确认项目配置可恢复。

以上全部通过，才算“搭建成功”。任何 provider 未授权、模型不可用或 role 无法启动，都不应跳过。

## 常见问题

### `ccb: command not found`

执行 `npm prefix -g`，把其 bin 路径加入 shell 的 `PATH`；重新开终端后再执行 `command -v ccb`。不要用 sudo 随意把全局 npm 包安装到别的用户目录。

### CCB 启动但 provider pane 立即退出

依次在普通终端独立运行 `codex`、`claude`、`opencode`，处理登录、模型或更新提示；确认 `command -v codex` 等返回真实路径；再运行 `ccb doctor`。不要从运行中的 `.ccb/agents/*/provider-state/` 拷贝认证文件。

### 模型不可用或套餐不匹配

模型名称、服务层级和高推理参数依赖账号。把 `.ccb/ccb.config` 的 `model` 和 `startup_args` 改为用户本人 CLI 已确认的可用组合；先 `ccb reload --dry-run`。不要为了启动成功而把 provider URL、API key 或账号令牌写进 config。

### 配置修改没有生效

确认改的是目标项目的 `.ccb/ccb.config`，不是另一个项目或 `~/.ccb/ccb.config`。先执行 `ccb reload --dry-run`；若报告拓扑变更不支持热加载，先确认没有任务，再在**目标项目目录**执行 `ccb kill` 后重新 `ccb`。

### reviewer 看到了旧上下文

这不是 reviewer 的判断问题，而是流程没有遵守 fresh review。先 `ccb clear reviewer`，再重新发送包含 exact-HEAD 的审查任务。不要在没 clear 的 reviewer 对话上追加“请重新审”。

### 多个 agent 同时改了同一文件

立即停止写入，保留工作区证据，由 main 划定唯一写者与 worktree。以后严格执行 developer 唯一写者；knowledge_keeper 仅在 developer 停止后工作。只读 agent 的 prompt 必须写明“禁止写文件”。

### tmux 会话或窗格残留

确认当前目录确实是目标项目后，先用 `ccb doctor` 看诊断；正常关闭使用 `ccb kill`。只有明确确认无活跃任务、普通关闭失败时，才考虑 `ccb kill -f`。不要在不相关项目目录运行强制清理。

## 提交问题报告需要附带什么

- 操作系统与终端（Linux/macOS/WSL，shell）。
- `ccb version`、`codex --version`、`claude --version`、`opencode --version`（可选）。
- 完整但已脱敏的错误文本和触发步骤。
- 是否在项目根目录、是否有活跃任务、是否刚改过配置。

不要附带：`~/.codex/auth.json`、`~/.claude.json`、`.env`、`.ccb/agents/*/provider-state`、数据库文件、cc-switch 数据库、cookie、完整日志或任何 token。
